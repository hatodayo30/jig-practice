# ship-branch

現在の作業ブランチの変更を「コミット → push → PR作成 → mainへのマージ」まで一気通貫で進める。

## 実行手順

1. **状態確認**
   - `git status` / `git diff` / `git log --oneline -10` で、変更内容・作業ブランチ名・既存のコミットメッセージの文体を確認する
   - `git branch --show-current` の結果が `main` の場合は中断し、ユーザーに作業ブランチの作成を確認する

2. **コミット**
   - 変更ファイルは `git add -A` / `git add .` を使わず、個別にファイル名を指定してステージする
   - コミットメッセージは日本語で、「何を・なぜ変更したか」を1〜3行程度で簡潔にまとめる。文体は直近のコミットログに合わせる
   - コミット前に、ステージ内容とメッセージ案を必ずユーザーに提示する
   - コミットは以下の形式で作成する(HEREDOCを使い整形を崩さない):
     ```
     git commit -m "$(cat <<'EOF'
     <日本語のコミットメッセージ>

     Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
     EOF
     )"
     ```
   - `--amend` や `--no-verify` は使わない。pre-commit hookが失敗した場合は原因を修正し、新規コミットとしてやり直す

3. **push**
   - リモートへの操作となるため、実行前に必ずユーザーに確認を取る
   - `git push -u origin <現在のブランチ名>` を実行する
   - force pushは行わない

4. **PR作成**
   - `gh pr create` で base を `main` としてPRを作成する
   - タイトルは日本語で簡潔に(70文字以内目安)、本文には変更概要とテスト観点を箇条書きで記載する
   - 既にそのブランチのPRが存在する場合は新規作成せず、既存PRの情報を確認してユーザーに提示する
   - 例:
     ```
     gh pr create --title "<日本語タイトル>" --body "$(cat <<'EOF'
     ## 概要
     - <変更点1>
     - <変更点2>

     ## テスト
     - [ ] <確認項目>
     EOF
     )"
     ```

5. **マージ**
   - CI状況やレビュー有無をユーザーに確認する
   - ユーザーから明示的なマージ承認を得てから `gh pr merge <番号> --squash`(またはユーザー指定の方法)でmainにマージする
   - マージ後、`git checkout main && git pull` でローカルmainを最新化することを提案する

## 注意事項

- push・PR作成・マージはいずれも共有状態に影響する操作のため、各ステップでユーザーの承認を得てから実行する
- `--force` / `--no-verify` / `-i` 系のオプションは使用しない
- 何を確認済みで次に何をしようとしているか、各ステップの節目でユーザーに一言報告する
